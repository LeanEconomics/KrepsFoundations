# Proposal: Kreps, *Microeconomic Foundations I: Choice and Competitive Markets*, in Lean

**Source.** David M. Kreps, *Microeconomic Foundations I: Choice and Competitive Markets*,
Princeton University Press, ISBN 978-0-691-15583-8. The local source is `Kreps2012.pdf`;
its copyright page says 2013. This proposal follows that copy: 16 chapters and eight
mathematical appendices, in a 584-page PDF. Printed page `p` is PDF page `p + 20`
(one-based numbering). Citations below use printed pages. The PDF has an imperfect text
layer; mathematical statements and numbering must be checked against the page images.

**Target.** `LeanEconomics/KrepsFoundations`, with one independent Lean/Mathlib project
per chapter under `Volume1/`, completed one chapter at a time in book order.

**Reference.** [LeanEconomics/DynamicProgramming](https://github.com/LeanEconomics/DynamicProgramming),
inspected at commit [`d39805f553dfb9619271b32bbf858d3162ca7e4e`](https://github.com/LeanEconomics/DynamicProgramming/tree/d39805f553dfb9619271b32bbf858d3162ca7e4e).
Follow its proposal format, independent chapter packages, Lean conventions, documentation,
dependency versions, verification scripts, and CI structure. The reference files are listed
in section 8.

Status: active implementation goal, 2026-10-21. Chapter 1 and Appendix 1 are complete
(213 theorems, 322 audited declarations); Chapter 2 is active with 246 new theorems audited.
The user authorized continuous chapter-by-chapter work through the whole volume.
Chapters 2-16 remain incomplete; source maps and audit records track actual progress.

### Independent projects and reuse

There is no root Lake library and no Lake dependency on another chapter or on the
DynamicProgramming repository. Earlier definitions and supporting lemmas are copied into
each chapter that needs them, following the reference's self-contained-project convention.
Copies live in the destination chapter's namespace and are included in its audit.

Record the originating chapter or upstream file and commit for copied material. Preserve
copyright headers and attribution when adapting Apache-licensed reference code. Reusing a
result requires checking its hypotheses against Kreps's statement; a similarly named
theorem is not sufficient. Changes to a copied lemma require reviewing the chapters that
carry that lemma. Document those copies in their source maps.

Use ordinary ignored `.lake/` folders initially on this Windows workspace. The reference's
Dropbox-specific symlink placement is a local storage arrangement, not a proof dependency.
Keep the supplied textbook available locally and exclude it from version control when the
repository is initialized.

### Lean source and documentation

1. **Namespaces.** `Kreps.<Project>`, for example `Kreps.ChoicePreferenceUtility`.
   Use subject-named modules and a root import file, matching the reference.
2. **File format.** Apache copyright/author header; explicit imports; a `/-! ... -/`
   module introduction giving the book section, pages, definitions, and principal results;
   then namespace, variables, definitions, and proofs. Use Mathlib formatting and linters.
   Credit actual contributors; do not copy another author's name onto original work.
3. **Names and citations.** Preserve source numbering in public entry points such as
   `proposition_1_2`, `proposition_1_2a`, and `problem_1_8`. Helpers have descriptive names.
   Docstrings cite `Kreps I, Prop. 1.2, p. 4` or `Kreps I, Problem 1.8, p. 26`.
   Appendix names retain their prefix, for example `proposition_A4_7`.
4. **Exact economic scope.** Prove the book's statements in their stated domains, including
   their generality and boundary cases. A finite version of an infinite-set result, or a
   sufficient condition substituted for an equivalence, is partial progress only.
5. **Explicit assumptions.** Separate definitions from additional hypotheses. State
   nonemptiness, completeness, transitivity, continuity, convexity, local nonsatiation,
   positivity, differentiability, constraint qualifications, integrability, and market
   completeness precisely where each theorem needs them.
6. **Coverage.** Account for every definition, assumption, numbered result, substantive
   mathematical claim, mathematical example, and in-text/end-of-chapter problem. Include
   numbered results appearing inside problems. Formalize every provable mathematical
   problem, with separate entries for materially different subparts. Record discussion,
   plotting, and purely numerical tasks as such; still prove their mathematical claims.
7. **Corrections.** Inspect the original page before calling something an error. For a false
   claim, aim to prove a counterexample and a corrected result. Record the original scope,
   change, reason, and Lean names in `docs/corrections.md`. An OCR mistake is a transcription
   issue, not a textbook correction. Never silently strengthen assumptions.
8. **Proof standard.** No `sorry`, `admit`, new axioms, `unsafe`, or `native_decide`.
   Allowed transitive axioms are exactly `propext`, `Classical.choice`, and `Quot.sound`.
   Mathlib results may be used with an explicit bridge to the book's statement. Missing
   mathematics becomes a proof task, not an assumed conclusion. If a result remains
   conditional or unresolved, label it openly and leave the chapter incomplete.

### Mathematical representations

| Object | Planned representation and check |
| --- | --- |
| Alternatives and preferences | An arbitrary type `X` and explicit relation `X → X → Prop`; completeness and transitivity as hypotheses. Do not impose antisymmetry, since distinct alternatives may be indifferent. |
| Choice | A set-valued map on feasible menus, with `c A ⊆ A`. Keep the menu domain explicit; the initial full-domain model and the restricted-domain problems must both be expressible. Finite nonemptiness is separate from nonemptiness on arbitrary menus. |
| Utility representation | A real-valued function and an explicit equivalence `pref x y ↔ u y ≤ u x`. Use `Set.Finite`/`Fintype` only for results that need finiteness. |
| Commodity bundles | A finite-dimensional Mathlib real space, using `Fin k → ℝ` for coordinates and an explicit nonnegative-orthant subset/subtype. Use `EuclideanSpace ℝ (Fin k)` where inner products or calculus need its structure, with explicit transport lemmas if both forms occur. |
| Demand and supply | Set-valued argmax/argmin correspondences. Introduce a chosen function only after proving existence, and uniqueness when the statement requires a unique choice. |
| Values and duality | Real values only after proving existence/finiteness or on a precisely defined domain; use extended values where the book permits unbounded profit, expenditure, or utility. |
| Lotteries and uncertainty | Finitely supported distributions for simple lotteries; general probability measures and integrals where Chapter 5 requires them. Do not replace arbitrary finite support on an infinite outcome set with a finite outcome space. |
| Time, agents, and markets | Finite index types and explicit event trees where the book is finite; actual infinite sequences and convergence hypotheses for infinite-horizon results. |
| Correspondence continuity | Preserve Kreps's closed-graph/sequential notion of upper semicontinuity. Prove its relationship to neighborhood-based upper hemicontinuity under the needed local-boundedness and compactness conditions; do not identify them by notation alone. |

These are implementation choices to be checked during the first chapter that needs them.
They do not change a source theorem's hypotheses.

## 5. Execution order and chapter workflow

**Order.** Complete Chapters 1-16 in printed order. Appendix prerequisites are developed
when first needed, with the ownership schedule above. No later economic chapter needs to
be formalized merely to provide a missing mathematical lemma. If the book postpones a
proof, bring the necessary supporting argument forward and document its source.

For each chapter:

1. **Read and inventory.** Read its complete pages and required appendix material. Create
   `docs/source-map.md` with entries for definitions, assumptions, every part of numbered
   results, significant unnumbered claims, examples, and every problem/subpart. List
   pending work explicitly in the Lean column; never use an invented Lean declaration
   name as if it already exists.
2. **Assess dependencies.** Identify the exact Mathlib declarations and previously proved
   modules to reuse. Check their hypotheses, spaces and versions. List missing results
   and the intended proof route before relying on them.
3. **Create the package.** Add the standard files, pinned dependencies, namespace, verifier,
   notices and CI entry. Copy the necessary prior modules with provenance. The first
   chapter also establishes the root README, license and repository conventions.
4. **Formalize in source order.** Definitions first, supporting lemmas next, then public
   source-numbered results and problems. Implement counterexamples where appropriate.
   Maintain an acyclic import order, even when a textbook proof appears later.
5. **Review fidelity.** Check the Lean statement against the actual page: quantifiers,
   domains, strict/weak inequalities, assumptions, conclusion, and every equivalence
   direction. Check examples establishing that the hypotheses are jointly satisfiable,
   especially for long assumption bundles and equilibrium models.
6. **Verify.** Run the complete package build and fresh proof audit. Keep module lists,
   theorem counts, source maps, corrections and README tables in agreement. Run the
   verifier's failure-path tests when establishing or modifying the verification setup.
7. **Close the chapter.** Mark it complete only after all mathematical coverage is proved
   or a false source statement is explicitly refuted/repaired. Document nonmathematical
   exclusions individually. Update the root index and this proposal, then move to the
   next chapter. An unresolved theorem remains an open item, not a completed milestone.

Use chapter-specific branches based on the completed prior chapter and keep each
chapter reviewable as a unit. Local Git work began on
`kreps-ch1-choice-preference-utility`. Publication is separate from the local
chapter-by-chapter implementation goal.

## 7. Verification and completion criteria

From an implemented chapter folder, use the same commands as the reference:

```sh
lake exe cache get
python -m unittest discover -s scripts -p 'test_*.py' -v
python scripts/verify.py
```

The verifier, rather than a manually maintained certificate, must:

- Build the complete library and check module/declaration inventories and theorem counts.
- Generate a fresh source audit that re-elaborates the contributed proofs without trusting
  precompiled copies of those project proofs.
- Reject warnings, forbidden proof shortcuts, placeholders and unexpected axioms.
- Audit each named declaration's transitive axioms against the three-axiom allowlist.
- Write the generated proof-check record and source hashes to `verification/verification.json`.

Retain the reference verifier's guarantees when adapting paths or supporting Windows.
Any required portability change gets its failure-path tests; a platform workaround must
not disable a check. CI runs each implemented chapter independently on pushes and pull
requests, following the reference's pinned setup and cache-fetch procedure.

Kernel acceptance establishes the formal theorem from its hypotheses. The separate
source-fidelity review establishes that this is the intended economic theorem; both are
required. README theorem counts do not measure textbook completeness by themselves.

**Volume completion** requires sixteen passing independent packages, complete chapter and
appendix source inventories, documented corrections and nonmathematical exclusions,
consistent dependency pins and provenance, and a final root index reporting only verified
coverage. There are no completed proofs or verification results to report at this stage.
